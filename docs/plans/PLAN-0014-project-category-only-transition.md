# Plan: ProjectCategory-only frontend transition

Date: 2026-09-15.
Status: completed. Explicitly approved and completed on 2026-09-15, including the UI approval candidates. Production deployment and data migration remain outside this authorization.

## Goal

Replace the authenticated application's fixed `scope` classification with the Project's server-backed Category across Projects, Home, Tasks, Journals, Milestones, Library, sidebar counts and saved Dashboard configuration. Category UUID is identity; names are mutable display values. Preserve the existing application shell, Korean presentation, resource workflows and session protections.

The user's new direction explicitly replaces the scope-preservation constraint in [the earlier Category Decision](../decisions/project-category-boundary.md). PLAN-0013 remains completed historical work. This Plan does not silently edit that Decision or activate itself: record the new architectural boundary in the Decision index when implementation is approved, retaining history rather than rewriting earlier acceptance.

## Scope

- In scope:
  - All authenticated business reads/writes on v2, while authentication and Category CRUD remain v1.
  - Category-only Project forms/presentation; shared Category filters and URL state; Project-derived child classification; nullable Project assignment for Links.
  - Category counts, Overview buckets, Dashboard schema 2 and missing-reference UX.
  - Response freshness metadata, cursor/cache invalidation, versioned immutable creation intents and deployment compatibility.
  - Unit, mocked browser, real-backend, responsive and legacy-isolation regression coverage.
- Out of scope:
  - Backend schema changes, production migration execution, production UUID manifests or restoring a database.
  - Category name-based identity, scope-to-Category inference, fixture/localStorage business authority.
  - Independent child-resource Category assignment, a new Deploy service, new colors/icons stored on Categories, or unrelated UI redesign.
  - Deleting historical scope fixtures, OAuth scopes, completed Plans or old replay payload fields merely to obtain a zero-text-match audit.

### 4. Freshness, errors and session preservation

- Category UUID/name reference data remains separate from business entity revisions. Rename refreshes the reference map and visible labels without requiring a Project/child revision increment. Category membership changes refresh Project lists/details, affected child lists/details/stats, Overview, Category counts and derived Link views. Remove the existing category-only suppression of these dependency refreshes.
- Category creation/deletion refreshes options/counts; deletion also refreshes Dashboard selectionState, without pretending Dashboard revision changed. Never invalidate every child list on an unrelated name-only change.
- Add generation- and cancellation-aware response metadata observation after a response has been validated. Keep per-query observation stamps and a monotonic per-session workspace watermark. Equal/lower stamps never overwrite newer derived data; absent replay headers never reset the watermark or make a historical snapshot current.
- Own mutations use explicit dependency invalidation. A higher observation from an external/unknown change marks previously observed older queries stale and schedules bounded, coalesced refresh of visible dependent queries; inactive entries refresh on demand. Seed/finish the mutation/read before follow-up invalidation so a callback cannot cancel its own successful operation. Test out-of-order stamps, invalid/missing headers and loop prevention. Resource edit revisions remain the PATCH/DELETE concurrency tokens; Link ordering still uses collectionRevision.
- No background polling or full workspace remount is introduced. Preserve the completed 30-second focus/visibility session check, same-identity DOM/scroll/modal/Store retention, failed-check mutation gate and explicit retry, hard logout/cross-tab/BFCache/security boundaries, generation partitioning and stale-response rejection. `/me` without a freshness header does not trigger business refetch.
- Keep existing CATEGORY_IN_USE, CATEGORY_NAME_CONFLICT, PROJECT_ARCHIVED, REVISION_CONFLICT, QUOTA_EXCEEDED, IDEMPOTENCY_KEY_REUSED and validation recovery. INVALID_CURSOR restarts the relevant cursor chain after retaining an actionable error; never append a page from another filter. API_VERSION_RETIRED (410) requires current-read reconciliation/update guidance, not automatic new creation.
