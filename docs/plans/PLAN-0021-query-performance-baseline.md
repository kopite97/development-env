## Goal

기존 API와 Swagger를 기준으로 페이지 이동·편집창 열기의 반복 요청과 화면 대기를 측정하고, 프로젝트 캐시 개선의 대상과 검증 기준을 확정한다. 이번 PLAN은 진단·측정이며 성능 개선 구현은 후속 PLAN에서 수행한다.

## Scope

- In scope:
  - 홈·프로젝트 목록/상세·할 일·프로젝트 선택 UI의 요청 흐름 조사.
  - 기존 Swagger/OpenAPI와 실제 응답의 조회·변경 계약 확인.
  - 격리된 검증 환경의 브라우저 측정 도구와 재현 자료 작성.
- Out of scope:
  - 캐시 정책·화면 동작 변경, TanStack Query 전환, 신규 의존성 도입.
  - 백엔드/API/Redis/DB 스키마 변경, 배포, 운영 데이터 변경·부하 테스트.
  - 전체 로그아웃, XSS·CSP 개선.

### Session 2 — 브라우저 기준 측정

- [x] 아래 시나리오를 같은 데이터·조회 조건으로 측정한다. 기본은 production build이며 개발 모드의 StrictMode/HMR 요청과 구분한다.

| 시나리오                         | 확인할 내용                                     |
| -------------------------------- | ----------------------------------------------- |
| 로그인 확인 후 홈 최초 진입      | 인증 대기, 대시보드 설정과 위젯 데이터의 의존성 |
| 프로젝트 목록 → 상세 → 같은 목록 | 캐시 삭제, 동일 조건 재조회, 페이지·스크롤 상태 |
| 홈 → 할 일 → 홈                  | 목록·통계·위젯의 중복 요청                      |
| 서로 다른 편집창 열기·닫기       | 프로젝트·카테고리 선택 데이터 재사용            |
| 격리 fixture에서 수정 후 재방문  | 필요한 갱신과 불필요한 무효화 구분              |

- [x] 최초 진입은 새 문서의 앱 메모리 캐시 없음, 재방문은 같은 로그인 세션 내 이동으로 정의한다. 브라우저 HTTP 캐시·네트워크 조건·서버 warmup 조건을 기록하고 구분한다.
- [x] API 요청 수·취소/실패/중복, 전송량, 요청 시작·종료, 사용자 동작부터 주요 데이터 표시까지의 시간을 수집한다. 주요 표시 지점은 화면별로 정의하고 `networkidle`만으로 완료를 판정하지 않는다.
- [x] 각 시나리오의 유효 측정 10회 이상을 기본으로 하고 원자료·중앙값·범위를 남긴다. 표본이 부족하면 p95나 운영 성능을 주장하지 않는다. 제외한 측정의 이유도 기록한다.
- [x] 요청 대기와 응답 이후 렌더링을 구분한다. 브라우저 관측 시간만으로 DB 실행 시간이나 서버 병목을 확정하지 않는다.

## Validation

### Static

- `npm run check:docs`, `git diff --check`로 문서 링크와 변경 내용을 확인한다.
- 측정 도구를 추가하면 구문 검사와 해당 시나리오 실행으로 검증한다. 앱 코드·의존성·설정의 무관한 변경이 없는지 확인한다.

### Runtime

- production build를 사용할 때 `npm run build` 성공 후 실제 API 연결 환경에서 측정한다.
- fixture/mock은 도구 동작 확인에만 사용하며 실제 서버 지연 측정으로 표시하지 않는다.
- 최초/재방문/변경 후 시나리오에서 인증 상태와 표시 결과가 정상인지 확인한다. 같은 조건의 반복 측정과 원자료로 요약값을 재현한다.
- 환경이나 인증 정보가 없어 측정하지 못하면 완료 처리하지 않는다. 수행한 대체 조사와 재개 조건을 기록한다.
